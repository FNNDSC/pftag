= pftag: tags, functions and templates
:toc:

== Abstract

This document is the reference for writing pftag templates: the grammar of a tag, how names are resolved, how functions are chained and given arguments, how markers are escaped or changed, and what every built-in tag and function does. It is written for the person typing a template on a command line, such as `pfdo_run --exec` or a `pflog` URL, and for the developer registering tags for them.

== A template

A template is ordinary text. Anything that is not a tag passes through unchanged. A tag begins with the tag marker, `%` by default, followed immediately by a name:

----
run-%timestamp-on-%platform.log
----

Processing replaces each tag with its value and leaves the rest alone:

----
run-2026-10-13T21:40:12.118-04:00-on-Linux.log
----

A `%` that is not followed by a letter is not a tag and stays as it is, so `100% done` is unchanged. A `%` followed by a letter that does not begin a known name is an unknown tag: it is left exactly as written, reported in the result's `unknownTags`, and, under `--strict`, fails the run. Unknown tags are kept rather than erased because a template that reaches a tool through several layers of quoting is easier to debug when the tag that did not resolve is still visible in the output.

== Names

A name is letters and digits, starting with a letter. Names come from two places: the core tags every engine knows, and the lookup dictionaries a caller registers. When a tag could be read as more than one name, the longest known name wins, so a tag may run straight into other text without a separator: with `subject` registered, `%subject-report.txt` becomes `sub-01-report.txt`, and with both `in` and `inputWorkingDir` registered, `%inputWorkingDir/x` resolves the long name. A registered name shadows a core tag of the same name.

The core tags:

[cols="1,3"]
|===
| tag | value

| `%literal` | the word `literal`; its use is as a carrier for `echo`, below
| `%os` | `os.name`, such as `posix`
| `%platform` | `platform.system()`, such as `Linux`
| `%release` | `platform.release()`, the kernel version
| `%machine` | `platform.machine()`, such as `x86_64`
| `%arch` | `platform.architecture()` joined with `-`, such as `64bit-ELF`
| `%timestamp` | the current local time in ISO 8601 with its UTC offset, computed when the template is processed
|===

Lookup dictionaries are registered by the program using pftag, or on the command line as JSON:

----
pftag --lookupDictAdd '{"run": {"subject": "sub-01", "session": "ses-2"}}' --tag "%subject/%session"
----

A dictionary has a name, used only for reporting, and maps tag names to values. The 1.x form, a JSON list of such objects, is still accepted. A tag name may not contain any of the four marker characters or a backslash, since the parser could not then tell where the name ends.

== Functions

A tag's value can be passed through functions written after the name between two function markers, `_` by default:

----
%timestamp_md5_
----

The order is the tag first, then what to do to it: Reverse Polish, the order of a UNIX pipe. Several functions chain with the function separator, `,`, each receiving the previous one's result:

----
%timestamp_chrplc|:|-,md5|6_
----

reads: take the timestamp, replace each `:` with `-`, hash to six characters. Arguments follow a function's name after the argument marker, `|`, and are separated by it. A function that needs an argument it was not given fails the tag: the tag is left as written, the result's `status` is False and `errors` says which function and why, and the command exits 1. An unknown function fails the same way.

Text after the closing marker is kept, so an extension can follow a function:

----
%inputWorkingFile_rmext_.jpg
----

The closing marker is required for a chain to be a chain. `%literal_md5` with no closing marker is the tag `%literal` followed by the text `_md5`, since without the marker there is no way to tell a function from an underscore in the surrounding text.

The built-in functions:

[cols="2,4"]
|===
| function | effect

| `echo\|<text>` | replace the value with `<text>`. With `%literal` this injects text into a template so that later functions can work on it.
| `md5[\|<chars>]` | the MD5 hex digest of the value, cut to its first `<chars>` characters when given.
| `chrplc\|<target>\|<new>` | replace every `<target>` with `<new>`. `<target>` is taken literally; written as `re:<pattern>` it is a regular expression.
| `strrepl\|<target>\|<new>` | the same, under the name pfdo_run used.
| `strmsk\|<mask>` | for each position of the mask, `*` keeps the value's character and any other character replaces it; positions beyond the mask are kept. `%platform_strmsk\|l****_` turns `Linux` into `linux`.
| `rmext` | drop the value's last extension: `brain.nii.gz` becomes `brain.nii`; apply twice for `brain`.
| `upper`, `lower` | change case.
| `dcmname[\|<seed>[\|<tail>]]` | a DICOM-style `LAST^FIRST` name. The same `<seed>` always produces the same name, so a subject can be given a stable pseudonym; `<tail>` is appended, as in `%NAME_dcmname\|foobar\|^ANON_`.
| `name` | the same as `dcmname`.
|===

The recurring idiom for protected text is `echo` followed by `md5`:

----
%literal_echo|Subject12345,md5|5_
----

The literal subject identifier never appears in the output, only its hash, and anyone who knows the identifier can recompute the hash to find its records.

== Escaping

A backslash before any of the four marker characters, or before a backslash, keeps it literal, inside or outside a tag. `\%platform` is the text `%platform`; inside an argument, `%literal_echo|a\,b_` yields `a,b` and `%literal_echo|a\|b_` yields `a|b`. Elsewhere a backslash is an ordinary character.

== Changing the markers

The four characters are options, on the command line and in `TagOptions`:

[cols="1,1,3"]
|===
| option | default | role

| `--tagMarker` | `%` | opens a tag
| `--funcMarker` | `_` | opens and closes the function chain
| `--funcArgMarker` | `\|` | separates a function from its arguments and the arguments from each other
| `--funcSep` | `,` | separates chained functions
|===

Each must be a single character, they must all differ, and none may be the backslash. Changing them is useful when a template lives inside something that already uses `%` or `_`, such as a `printf` format or a shell `--exec` string with many underscores in file names:

----
--tagMarker "@" --funcMarker "[" --funcArgMarker "," --funcSep "|"
@tag[func,a1,a2|func2,b1[
----

== Reading a result

The command prints the processed text. With `--json` it prints the whole result: `result`, `template`, `tagsFound` in order, `unknownTags`, `functionsApplied` as `name|arg|arg` entries in order, `errors`, and `status`. The library returns the same as a `TagResult` dataclass. `status` is True unless `strict` met an unknown tag or a function failed; the processed text is always returned, with any failing tag left as written.

== Registering tags from a program

----
from pftag import Pftag, TagOptions

tagger = Pftag(TagOptions(lookups={"pfdo": {
    "inputWorkingDir": "/in/sub-01",
    "outputWorkingDir": "/out/sub-01",
    "inputWorkingFile": "T1.nii.gz",
}}))
tagger("convert %inputWorkingDir/%inputWorkingFile %outputWorkingDir/%inputWorkingFile_rmext_.jpg").result
----

`lookup_add(name, values)` registers a dictionary after construction and replaces one of the same name; values are stringified. Functions are added through a `FunctionRegistry` passed to `Pftag`: `registry.add("shout", lambda value, args: value.upper() + "!")`. A function receives the value so far and the list of arguments written in the template, and returns text; it raises `FunctionError` for arguments it cannot use.

== Differences from 1.x

Names are now matched longest first against the known names, not by substring, so `%os` no longer matches inside `%outputWorkingDir` and a tag may run straight into text. Function chains are parsed to their closing marker, and arguments may contain escaped markers. `strmsk` no longer shortens the value. `chrplc` is literal unless written `re:`. `rmext` and `strrepl` come from pfdo_run; `upper` and `lower` are new. `dcmname` seeds its own generator and builds the name from a first and a last name, so a prefixed name can no longer break it. The result is a dataclass rather than a dictionary.
