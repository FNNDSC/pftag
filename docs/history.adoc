= pftag: history
:toc:

== Abstract

pftag was created in March 2023 to lift the `%tag` template idea out of pfdo_run into a package other tools could share, reached 1.3 within two months, and was rebuilt in October 2026 as version 2 with a real tokenizer so that it could become the one template processor of the pf* family.

== Before pftag

The grammar's first home was pfdo_run, in 2020: a `%` marker, the three working-directory tags, every command-line option reachable as a tag, and functions written as a prefix, `%_rmext_inputWorkingFile`. It did what pfdo_run needed and no more, and its parser was a substring search over `%`-delimited chunks.

== 2023: a package

The first commit, on 10 March 2023, set pftag up as both a command and a module, with a core set of tags describing the machine and the moment and the functions pflog's telemetry URLs needed: `md5`, `chrplc`, `strmsk`, `echo`, `dcmname`. The grammar was changed from pfdo_run's prefix form to a suffix form, `%tag_fn|arg_`, closed by a marker, which allowed functions to chain and arguments to be delimited. Versions 1.2.x through March 2023 fixed typos and a Python 3.6 compatibility hack; 1.3.0 on 27 April 2023 added externally supplied lookup dictionaries, the mechanism by which a calling program gives a template its own tags, and 1.3.2 the `lookupDict_add` helper. pflog adopted it at once; pfdo_run never did, and the two grammars coexisted from then on.

== 2026: version 2

By 2026 pftag had two kinds of debt. The first was the same as its siblings': `pudb` imported at module level, `XDG_CONFIG_HOME` overwritten at import, the global `Faker` reseeded by `dcmname`, `--version` exiting 1, `python -m pftag` broken, a Docker image built by a workflow copied from another repository that pushed its README to the wrong Docker Hub project, and a test suite that passed on Python 3.11 and failed on 3.14 for an argparse quirk. The second was in the parser itself: names and functions were matched by substring, so `%os` fired inside `%outputWorkingDir` and any argument containing `md5` invoked `md5`; chained functions were applied by repeatedly replacing text in the whole template, so a value that appeared elsewhere was rewritten too; `strmsk` truncated its input; `chrplc` treated every target as a regular expression.

The decision in October 2026, taken while rebuilding the pfdo family on pftree 4, was that the family should have one template grammar and that pftag's suffix form was the better one: its closing marker is what makes chaining and trailing text unambiguous, and tag-then-function is the order of a pipe. Version 2.0.0 therefore rebuilt the engine as a single-pass scanner with longest-first name matching and a proper chain parser, moved options, tokens and results into dataclasses, made the function registry an object with pfdo_run's `rmext` and `strrepl` added alongside `upper` and `lower`, fixed the functions, added `--strict` and `--json`, removed the debugger, the environment side effects and the Docker image, and added tests, continuous integration and publication from a tag. pfdo_run 4 is the first package to resolve its templates with it.
